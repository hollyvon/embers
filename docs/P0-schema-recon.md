# P0 — Claude Code JSONL schema recon (structure only; zero transcript content)
*Written from a full pass over one operator's local corpus with `python3 -I tools/schema_probe.py --out P0-schema-report.json` (structure only; the report file is local and git-ignored). The per-corpus counts, sizes, dates and version ranges that the probe prints were removed from this public copy on purpose; run the probe on your own machine for your own numbers. Observed: many Claude Code versions across a two-month window, `entrypoint = claude-desktop`, `userType = external`. Schema drifts across versions — the parser must tolerate unknown/missing keys.*

## (a) Corpus layout
- Files live under `~/.claude/projects/<projdir>/`: top-level session files `<session-uuid>.jsonl` (the large majority) and subagent files `<parent-session-uuid>/subagents/agent-<17-hex>.jsonl`.
- File sizes are heavily right-skewed: most files are a few MB, a long tail reaches tens of MB.
- Every line is a single JSON object, UTF-8, `\n`-terminated; no unparseable lines were seen.
- Specific counts, byte totals and date ranges are deliberately omitted here (they profile one operator); the probe prints them locally.

## (b) Field inventory
Presence = % of ALL lines. Top-level keys (type in brackets). Nested keys are listed for the structurally important objects; the full path list (≈700 paths) is in `P0-schema-report.json` → `paths`.

**Envelope (on "conversation" records: user/assistant/attachment/system; 68.2% of lines):** `uuid` [str], `parentUuid` [str|null], `sessionId` [str; 97.5% — metadata records carry it too], `timestamp` [str; 78.3%], `type` [str, 100%], `cwd`, `gitBranch`, `version`, `entrypoint`, `userType`, `isSidechain` [bool] (all 68.2%).
**Optional envelope:** `isMeta` [bool, 0.3%], `slug` [str, 11.5% — human-readable session slug], `promptId` [str, 16.4%], `permissionMode` [str: `acceptEdits`|`auto`, user lines], `origin` {`kind`,`subkind`,`producer`,`runId`,`fireReason`} (7.2%, user lines), `agentId` (0.9%, subagent files), `requestId` [str, 30.5%, assistant], `sourceToolAssistantUUID` [str, 8.7%, tool-result user lines], `toolUseResult` (8.4%), `effort`/`perTurnEffort`/`advisorModel`/`requestedModel`/`apiBlockIndex`/`thinkingDurationMs` (assistant-side extras), `attributionSkill|McpServer|McpTool|Plugin|Agent`.
**`message` object (47.0%):** `role` [`user`|`assistant`], `content` [**string OR array of blocks**], and on assistant lines (30.5%): `id` [str `msg_…`], `model`, `type` (`message`), `stop_reason` [`tool_use`|`end_turn`|`refusal`|`stop_sequence`|null], `stop_sequence`, `stop_details`, `container`, `context_management`, `diagnostics`, `input_transformations`, and `usage`.
**`message.usage`:** `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` [int]; `cache_creation{ephemeral_5m_input_tokens, ephemeral_1h_input_tokens}`; `server_tool_use{web_search_requests, web_fetch_requests}`; `service_tier`, `speed`, `inference_geo` [str|null]; `iterations[]` (array of per-iteration usage objects, same int keys + `type`); `output_tokens_details{thinking_tokens}` (23.8%); `fallback_credit` [null].
**Models seen (assistant `message.model`):** several real ids + the literal `<synthetic>` (harness-injected assistant lines, e.g. errors). **No per-message dollar cost.** The only cost data is `type:"cost-state"` records (rare): `totalCostUSD`, `totalAPIDuration`, `totalAPIDurationWithoutRetries`, `totalDuration`, `totalToolDuration`, `totalLinesAdded|Removed`, `modelUsage{<model-id>:{…}}`, `hasUnknownModelCost`, `startTime`.
**Timestamp shape:** exactly one format on every timestamped line: `YYYY-MM-DDTHH:MM:SS.mmmZ` (UTC, ms, `Z`). Also `snapshot.timestamp`, `attachment.timestamp`, `backup.backupTime` use the same shape.
**ID shapes:** `uuid`/`sessionId`/`parentUuid`/`leafUuid` = lowercase hyphenated UUIDv4 strings; `message.id` = `msg_` + base62; `requestId` = `req_` + base62; tool_use `id` = `toolu_` + base62; subagent `agentId` = 17 lowercase hex chars (file `agent-<agentId>.jsonl`).

## (c) Record types (15) and shapes
Rough mix by line share: assistant ~30%, user ~16%, attachment ~14%, queue-operation ~10%, system ~7%, then last-prompt, custom-title, atis-latch, mode, file-history-snapshot, ai-title, bridge-session, agent-name (a few % each), file-history-delta and cost-state (rare). §f carries the same proportions as generator targets.
**There is NO `summary` record and NO top-level `tool_result` record type** (both assumed by the spec; see §g). Tool results are `user` records carrying a `tool_result` block.

Synthetic shapes (values are placeholders):

**Content blocks:** assistant lines are roughly equal parts text, thinking and tool_use; user lines are dominated by tool_result, with text and image blocks a small minority and `document` blocks rare. `tool_result.content` is a **string** or an **array** (text/image/tool_reference items). `message.content` for user lines is a string in the common human case (`origin.kind=human`) and an array otherwise. Tool names are dominated by Bash, Edit and Read, then WebSearch and Write, plus MCP tools (`mcp__<server-id>__<tool>`; server ids are opaque UUIDs or names).
**Key dict-keyed objects to special-case:** `snapshot.trackedFileBackups` (keys are absolute file paths — never treat as schema), `wireToolInputs` / `wireIngestContext` (keys are tool-use ids), `mcpMeta._meta` (keys vary), `modelUsage` (keys are model ids).
**⚠ Assistant messages are split across lines:** one API message (`message.id`) appears as 1–8 consecutive `assistant` lines, **one content block per line**, each with its own `uuid` but the same `message.id`/`requestId`, and `usage` repeated (so summing `usage` across lines over-counts). Distribution: about a quarter of messages are 1 line, half are 2, a quarter are 3, with a thin tail to 8. `stop_reason` is usually null on early blocks and set on the last.

## (d) Stitching rules
**1. Compaction does NOT start a new file.** It is in-file: a `system` record `subtype:"compact_boundary"` with `parentUuid:null` (a new chain root!) and `logicalParentUuid` = uuid of the last pre-compaction record (always in the same file; 27/27), plus `compactMetadata{trigger:"auto"|"manual", preTokens, postTokens, durationMs, cumulativeDroppedTokens, preservedSegment{}, preservedMessages{}, preCompactDiscoveredTools[]}`. It is followed by a `user` record with `isCompactSummary:true` (+ `isVisibleInTranscriptOnly:true`), content = the summary as a plain **string**, and a non-null `parentUuid` pointing at the boundary. Roughly one file in eight contains boundaries, mostly `auto`; a compacted file can hold several. Consequence: files normally have 1 root but 2–7 `parentUuid:null` roots when compacted (= boundaries + 1). **Pre-compaction text is fully retained in the file** (confirms the SPEC field note). A parser that follows only `parentUuid` will lose the pre-compaction chain; follow `logicalParentUuid` across the boundary, or simply order by file line order/timestamp.
**2. Resume/fork creates a NEW top-level file that re-copies history.** About a third of session files begin (almost always exactly as a contiguous prefix) with lines whose `uuid`s are identical to lines in one or more other files (roughly a sixth of all distinct uuids occur in more than one file; 1–8 owner files; copied prefixes run from a few hundred to a few thousand lines). In nearly all cases the copied lines have `sessionId` rewritten to the NEW file's own id (uuid and timestamps unchanged); rarely the copied prefix keeps the *original* file's sessionId, and one file was seen mixing several sessionIds. There is **no explicit "resumedFrom/parentSession" field and no leading `summary` record** — lineage is inferable only by uuid overlap. No `parentUuid` ever dangles across files (0 cross-file parents; every parent resolves in its own file).
**Stitching rule:** logical thread = connected component of files under the relation "shares ≥1 message uuid"; within a component dedupe messages by `uuid` (keep one copy; prefer the earliest-timestamp owner file as canonical, record all owner files), order by `timestamp` then line index. A file's *new* material = its lines whose uuid is not in an earlier-ordered file. `sessionId` is NOT a reliable thread key (rewritten on copy); the filename stem is the file's own session id (true for every top-level file except the mixed-sessionId case).
**3. Subagents/sidechains:** separate files at `<projdir>/<parent-session-uuid>/subagents/agent-<agentId>.jsonl`. Their lines have `isSidechain:true`, `agentId`, `sessionId` = the PARENT session's id (not the filename), and begin with a `user` record with `parentUuid:null` (own root). Types inside: user/assistant/attachment only (no metadata records). **No `isSidechain:true` line exists in any top-level file** (0). Link to parent: the parent's `Agent` tool_use and its tool_result `toolUseResult{agentId, agentType, totalTokens, totalToolUseCount, toolStats, usage…}` (rare) carry the `agentId`. Index sidechains as children of the parent session, flagged as subagent.
**4. Scheduled-task runs:** distinguishable at the first user message: a sizeable minority of files start with a user text whose first XML-ish tag is `<scheduled-task…>` (tag-name only recorded; the rest of the content is not reproduced here); the others start with plain text. Also `origin.kind:"task-notification"` (+`subkind:"scheduled-trigger"`; `producer:"session-task"`) marks injected notifications; `origin.kind:"human"` marks real human prompts. `origin` is absent on most user lines (tool results, meta), so "human prompt" = `type=user ∧ origin.kind=="human"` OR (origin absent ∧ content is not a tool_result ∧ isMeta≠true) — verify (§g).
**Other per-file facts:** first record type is usually `queue-operation`, else `custom-title`, or `user` for subagent files. Session title = LAST `custom-title` (else last `ai-title`); titles are re-appended repeatedly (dozens of custom-title lines per file is normal), same for `last-prompt`, `mode` → **dedupe metadata records, keep last**.

## (e) Noise profile (share of total bytes, whole corpus)
| class | % bytes |
|---|---|
| image base64 (`image` blocks, tool_result images; user image blocks + tool-result screenshots) | 40.2 |
| `toolUseResult` top-level structured duplicate of the tool_result (file contents, stdout, patches — mostly redundant with the `tool_result` block) | 25.8 |
| envelope/metadata/attachments/system/queue/snapshots (everything not itemized; includes attachment payloads, hook infos, file-history, usage objects) | 19.2 |
| thinking blocks (+ signatures) | 7.7 |
| tool_result text | 3.0 |
| assistant prose (text blocks) | 2.2 |
| tool_use `input` | 1.2 |
| human prose | 0.8 |
| inline `<system-reminder>` spans inside message text | ≈0.0 (reminders arrive as `attachment` records, 11.6% of lines carry `attachment.text`, bytes counted in envelope row) |
Caveat: image data nested inside `toolUseResult` is counted once there, not under images; true image share is somewhat higher. **Index-worthy prose (human + assistant text) ≈ 3% of bytes**; with tool_result text ≈ 6%; with thinking ≈ 14%. ~66–70% of the corpus is base64 + duplicated structured results → skip. Tool-related user lines slightly outnumber human prompts.

## (f) REQUIREMENTS for the synthetic fixture generator
A fake corpus must be a directory tree `<root>/<projdir>/…` with ≥3 project dirs (dir names = path-with-slashes→dashes style, arbitrary), UTF-8 JSONL, one object per line, deterministic (seeded). Required reproduction:
1. **Layout:** top-level `<projdir>/<uuid>.jsonl` sessions (~84%) and `<projdir>/<parent-uuid>/subagents/agent-<17hex>.jsonl` (~16%). Size distribution log-normal: real files start around tens of KB → for fixtures scale down 100–1000× but keep ratios: median ≈ 1×, p90 ≈ 15×, max ≈ 40×; plus a few tiny (<10 lines) files.
2. **Record types & mix (by line %):** assistant 30, user 16, attachment 14, queue-operation 10, system 7, custom-title 4, last-prompt 4, ai-title 2, atis-latch 2.4, mode 2.3, bridge-session 2.2, agent-name 2.1, file-history-snapshot 2.3, file-history-delta 0.2, cost-state 0.05. Include ALL 15 types. Do NOT emit `summary` records by default; emit a clearly-labelled variant flag (`--legacy-summary`) so ingest can be tested for tolerance of an unknown/legacy `{"type":"summary","summary":"…","leafUuid":"…"}` record.
3. **Envelope:** conversation records carry uuid, parentUuid, sessionId, timestamp (`YYYY-MM-DDTHH:MM:SS.mmmZ`, monotonic non-decreasing within a file except copied prefixes keep original), cwd, gitBranch, version (vary across ≥5 versions), entrypoint, userType, isSidechain. Metadata types omit uuid/parentUuid/(usually) timestamp but carry sessionId — except `file-history-*`, `cost-state`, `bridge-session` which may omit sessionId.
4. **Chain structure:** parentUuid forms a linear chain in a file with occasional side branches (rare); first record parentUuid null. Tool loop: assistant(tool_use) → user(tool_result, `sourceToolAssistantUUID` = that assistant uuid, plus `toolUseResult`) → assistant….
5. **Assistant splitting:** each API message = 1–8 consecutive lines, one content block each (distribution 24%/50%/23%/2%/tail), shared `message.id` & `requestId`, repeated `usage`, `stop_reason` null until last block. Some thinking blocks carry `signature`. Include `<synthetic>` model lines and `stop_reason:"refusal"` rarely.
6. **User content polymorphism:** string content; array with text; array with image block (base64, short fake data); `document` block (rare); tool_result with string content; tool_result with array content (text + image + tool_reference); `is_error:true` (~3.6% of blocks have is_error present).
7. **`origin` & meta:** ~45% of user-with-string lines `origin:{kind:"human"}`; some `task-notification` (+`scheduled-trigger` subkind, `producer:"session-task"`); `isMeta:true` rare; `permissionMode` ∈ {acceptEdits, auto}.
8. **Compaction:** in ~10% of sessions insert 1–3 `compact_boundary` system records (parentUuid null, logicalParentUuid → previous record, compactMetadata with trigger auto/manual, realistic token ints) followed by a `user` record `isCompactSummary:true, isVisibleInTranscriptOnly:true`, string content, parentUuid → boundary.
9. **Resume/fork copies:** ~30% of top-level sessions are produced by copying a contiguous prefix (a few hundred to a few thousand lines, scaled) of another session verbatim (same uuids/timestamps) with `sessionId` rewritten to the new file's id (variant ~6%: sessionId left as the original; variant: one file containing mixed sessionIds, non-contiguous shared lines), then appending new records. Include chains: A→B→C (C copies B's whole content incl. A's prefix) and fan-out (one parent copied by up to 8 children). Ground-truth manifest (`truth.json`: component membership, canonical owner per uuid) must be emitted for tests.
10. **Subagents:** parent has `Agent` tool_use + tool_result with `toolUseResult.agentId`; child file: all lines `isSidechain:true` + `agentId`, `sessionId` = parent id, first user record parentUuid null; types limited to user/assistant/attachment; 10–30 lines each.
11. **Scheduled-task runs:** ~35% of sessions open with a user text beginning with a `<scheduled-task …>` XML-ish tag (synthetic body), others plain; sprinkle `task-notification` origin records.
12. **Metadata churn:** title/last-prompt/mode/agent-name/atis-latch records re-emitted many times per file (dedupe-last test); `queue-operation` triples (enqueue→dequeue, occasional remove) carrying `content`.
13. **Attachments:** types from the observed list (total_tokens_reminder dominant ~77%, task_reminder, skill_listing, deferred_tools_delta, file, edited_text_file, date_change, instructions, hook_additional_context…); payload in `attachment.text` (long, boilerplate — ~11.6% of lines have it).
14. **Noise mix (by bytes) to hit:** ≈40% image base64, ≈26% `toolUseResult` duplicates, ≈19% envelope/attachments, ≈8% thinking, ≈3% tool_result text, ≈2% assistant prose, ≈1% tool_use input, <1% human prose. (Generator may scale image payloads down but must keep image-bearing lines to the same *line share*, ~2–3%, and keep a few huge single lines — up to 5 MB — to test line-length limits.)
15. **Edge cases:** dict-keyed objects with path/ID keys (`snapshot.trackedFileBackups`, `wireToolInputs`, `mcpMeta._meta`); MCP tool names `mcp__<opaque>__<tool>`; unicode/emoji/RTL, embedded newlines and `<system-reminder>` text in content; `input` of a tool_use containing `__unparsedToolInput`; `error` objects on `api_error` system records with retryAttempt/retryInMs; `content: null`/empty-string content; truncated final line (partial JSON) in ≥1 file; a file being appended while read; CRLF absent; zero-length file; duplicate uuids within one file (check — see §g).
16. **Schema drift:** vary `version` and randomly drop optional keys; emit a few unknown extra keys so the ingester proves forward-tolerance.

## (g) Open questions
1. Resume semantics: is the copied prefix a *resume* or a *fork* (`--resume`/`/clear`/branch)? No explicit parent pointer exists; the uuid-overlap rule is inferential. Confirm by checking that every overlapping pair has the later-mtime file as the superset (not done) and decide canonical-owner policy.
2. The rare files whose copied prefix retains the ORIGINAL sessionId, and the one mixed-sessionId file: probably different resume modes; characterize with a larger sample.
3. Legacy `summary` records / `leafUuid` appear in older Claude Code versions; none in the recon corpus (all recent versions). Older transcripts on other machines would need the variant — keep tolerance.
4. Exact human-prompt predicate (origin.kind absent cases; `isMeta`; `queue-operation` content vs user records — queued prompts appear in BOTH `queue-operation.content` and later `user` lines, risking double-indexing).
5. Are `toolUseResult` and `tool_result` ever non-redundant (e.g. truncated model-side vs full UI-side: `contentNotInModelContext`, `persistedOutputPath` flags exist)? Decide whether to index toolUseResult.stdout instead of the block.
6. `thinking` blocks: index or not? (7.7% of bytes; privacy-heavy; signatures are opaque.) Policy decision for the owner.
7. Reminder text arrives via `attachment` records, not inline; confirm which attachment types carry user-meaningful text (e.g. `file`, `edited_text_file`, `queued_command`) vs boilerplate.
8. The recon corpus spanned only a couple of months: older sessions on disk may be pruned by Claude Code retention — confirm no cleanup setting is deleting history (SPEC says raw is kept forever; the *source* may not be).
9. Cost: no per-message USD; derive from `usage` + model price table, or use `cost-state` snapshots — decide which `mem` should expose.
